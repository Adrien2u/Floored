# The `.floored` format

The format is a **contract**, not an implementation detail. Any tool may read or
write these files; the schemas here are published so it can.

| Version | Schema                                           | Adds                                       |
| ------- | ------------------------------------------------ | ------------------------------------------ |
| 1       | [floored-v1.schema.json](floored-v1.schema.json) | room, roundTable, rectTable, fixture, note |
| 2       | [floored-v2.schema.json](floored-v2.schema.json) | seatingBlock                               |
| 3       | [floored-v3.schema.json](floored-v3.schema.json) | the optional `seating` block               |

## The guarantee

**Every future version of Floored opens every file written by any earlier
version.** ([ADR-0004](../adr/ADR-0004-file-format.md))

That is enforced rather than promised. `tests/fixtures/` holds one real file per
released version, and `src/lib/document/migration.test.ts` opens each of them on
every run — checking not merely that they parse, but that the geometry, the
metadata, and the computed capacity all still mean what they meant when the file
was written.

## Rules for changing the format

1. **Released schemas are never edited.** A published schema describes files that
   already exist in the world.
2. **Released migrations are never edited.** A migration step is the only record
   of what old files actually looked like.
3. **Every bump adds a fixture.** A version with no fixture is a version whose
   compatibility is untested.
4. **The version is an integer, not semver.** Semver invites arguing about
   whether a change is minor; an integer has no such ambiguity.

## Reading a file without Floored

Geometry is **integer millimetres** throughout, with +x right and +y down.
Display units are a presentation choice and never affect stored values, so a
file written by someone working in feet is byte-identical to one written in
metres for the same plan.

Seats are generated by the element that owns them and are never stored
individually ([ADR-0012](../adr/ADR-0012-seat-generation.md)). A table's seat
count is `seats`; a seating block's is `rows × columns`. A seat is addressed as
`(elementId, seatIndex)`.

Guests live in the top-level `seating` object, not among the elements. They have
no geometry, so they never appear on the drawing, and a reader that only wants
the floor plan can ignore the key entirely
([ADR-0013](../adr/ADR-0013-seating-model.md)). It is omitted from files with no
guest list, so a plan drawn before guests existed and one drawn without them are
byte-identical.
